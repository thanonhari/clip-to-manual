🧪 ที่มาของประโยคเปิด: ปิด loop ให้ครบวงจร
🔹 Peter โชว์โปรเจกต์เล็กชื่อ Nameplate จุดเริ่มคือเขามีทั้งเครื่องจริงและ VM ที่เป็น macOS ซ้อนกันหลายหน้าต่างจนงงว่าอันไหนคืออันไหน เลยสร้างป้ายชื่อถาวรแปะให้แต่ละเครื่อง
🔹 มีผู้ใช้ขอให้รองรับ Linux กับ Windows ซึ่งเมื่อก่อนงานแบบนี้ลำบาก เพราะ agent เขียนโค้ดให้ได้ก็จริง แต่ Peter ต้องไปหาเครื่อง Windows มาติดตั้งเอง เจอ error แปลกๆ ก็ copy กลับไปวางใน Codex เอง
🔹 นั่นคือที่มาของประโยคเปิดโพสต์ ถ้ายังทำแบบนั้นอยู่คือผิดวิธีแล้ว โจทย์ที่ถูกคือ จะยื่นเครื่องมืออะไรให้ Codex เพื่อให้มันวิ่งครบทั้งวงจรได้ด้วยตัวเอง
🔹 ระดับที่ 1: มีเครือข่ายส่วนตัวหรือใช้ Tailscale ที่มีเครื่อง Linux และ Windows ต่ออยู่ แล้วบอก agent ว่าใช้เครื่องพวกนี้ได้เลย ยิ่งถ้าเข้าผ่าน SSH ได้ก็ยกระดับขึ้นไปอีกขั้น
🔹 ระดับที่ 2: งานที่ต้องคุมหน้าจอด้วย ให้ยก VM ให้ agent ไปเลย 1 เครื่อง เพราะตอนนี้ Computer Use เก่งขึ้นมากจน agent รับภาพหน้าจอ คลิกเอง และทดสอบแบบ end to end ได้ครบ
🔹 ข้อจำกัดคือใน VM ตัว agent ไม่ได้ข้อมูล accessibility ได้แค่ภาพหน้าจอล้วนๆ อาจงมหาปุ่มเล็กๆ นานกว่าปกติ แต่เดี๋ยวก็เจอ Peter เลือก optimize ที่ความสามารถ ยอมเปลืองรอบเพิ่มอีกหน่อยก็คุ้ม
🔹 ปลายทางคือ agent ติดตั้งเอง รันเอง จับภาพหน้าจอเช็คเอง เจอ error หรืออะไรผิดคาดก็วนแก้ต่อเอง โดยไม่ต้องมีเรานั่งเฝ้าเป็น QA
🔹 Peter สารภาพว่ากว่าจะคิดได้ก็ใช้เวลานานจนน่าอาย ยุคแรกของ OpenClaw เขา build เสร็จ copy ลงโฟลเดอร์แชร์ ติดตั้งเอง แล้วนั่งคลิกทดสอบเองทุกจุด
🔹 Corey เสริมว่าถ้าไม่อยากคลิกตั้งค่า VM เอง ก็ใช้ Computer Use ช่วยตั้งค่า VM ให้ได้ด้วยซ้ำ

🤖 "agent ฉันรันได้ 50 ชั่วโมง" ไม่ใช่ประเด็น
🔹 คำถามยอดฮิตช่วงนี้คือจะปล่อย agent ทำงานยาวๆ ได้ยังไง Peter ตอบชัดว่าการคุยอวดกันว่า agent ของฉันรันต่อเนื่อง 20 ชั่วโมง 50 ชั่วโมง มันไม่ใช่ประเด็นเลย
🔹 คำถามที่ควรคิดหนักๆ คือ agent ของเราต้องการอะไรเพื่อทำงานชิ้นนั้นให้ออกมาดีที่สุด และเราจะสร้างระบบแบบไหนที่เพิ่มโอกาสให้ผลลัพธ์ออกมาตรงกับที่สั่งจริงๆ
🔹 การเขียนแผนละเอียดแล้วยิงงานทิ้งไว้หลายวันก็ทำได้ ในฐานะการทดลองสนุกๆ ว่ามันจะออกมาหน้าตายังไง แต่นั่นไม่ใช่วิธีหลักของเขา

⚡ สไตล์ Peter: มีไอเดียก็สั่งเลย แล้วขยับไปเรื่องถัดไป
🔹 Peter บอกตรงๆ ว่าแทบไม่เคยรู้ปลายทางชัดตั้งแต่แรก รู้แค่ทิศทางคร่าวๆ เลยต้องอาศัยลองและสำรวจไปเรื่อยๆ การนั่งเขียน spec ละเอียดยิบตั้งแต่ต้นจึงยากมากสำหรับเขา
🔹 วิธีทำงานจริงคือ มีไอเดีย สั่ง prompt แล้วขยับไปไอเดียถัดไปทันที วนแบบนี้จนบางช่วงมีงานวิ่งพร้อมกัน 20 30 40 ไปจนถึง 50 เรื่อง

🔹 แม้ agent จะเร็วขึ้นมาก แต่เวลาตั้งแต่สั่ง prompt จนงานพร้อมใช้จริงยังอยู่ราว 30 นาทีถึง 2 หรือ 3 ชั่วโมง เพราะหัวใจไม่ได้อยู่ที่เขียนโค้ดเสร็จ แต่อยู่ที่กระบวนการ review

🔁 auto-review: skill ที่เปลี่ยนวิธีทำงานของ Peter มากที่สุด
🔹 Peter มองว่า agent เขียนโค้ดคล้ายมนุษย์ คือพลาดได้ และหลายอย่างเพิ่งจะเห็นเอาตอนกลับมาดูรอบสอง
🔹 ทุกวันนี้เวลาเขียนโค้ดจริงเหลือแค่ราว 20% ที่เหลือหมดไปกับการตรวจทาน
🔹 กลไกของ auto-review คือเรียก Codex ตัวใหม่บน context สดขึ้นมา review งานทั้งหมด แล้วป้อนผลกลับให้ session เดิม
🔹 session เดิมจะตัดสินเองว่าคำติไหนมีประโยชน์จริง หรืออันไหนเกิดเพราะตัว review ไม่มี context เท่าคนลงมือทำ ถ้าเห็นด้วยก็แก้ ถ้าไม่ ก็เขียน comment อธิบายเหตุผลฝังไว้ในโค้ดเลย รอบถัดไปตัว review อ่านเจอจะได้ไม่ทักเรื่องเดิมซ้ำ
🔹 วนซ้ำแบบ recursive ไปเรื่อยๆ จนกว่า review จะไม่เจออะไรอีก บางงานจบใน 2 ถึง 3 รอบ บางงานลากถึง 10 หรือ 20 รอบ
🔹 เหตุผลเบื้องหลังคือพวกนี้เป็นเครื่องจักรเชิงความน่าจะเป็น เหมือนมนุษย์ review รอบเดียวก็ไม่มีทางเจอทุกจุด แต่ยิ่งวนซ้ำ ยิ่งเจอเพิ่มขึ้นเรื่อยๆ
🔹 ราคาที่จ่ายคือ session อาจช้าลงถึง 10 เท่า แต่ Peter ยืนยันว่าตั้งแต่ใช้ skill นี้ ความมั่นใจว่าของที่ ship ออกไปใช้งานได้จริงคือ โดยพื้นฐานแล้วมันใช้งานได้เสมอ
🔹 skill นี้เปิดเป็น repository สาธารณะ ใช้ได้ทั้งแบบ CLI เรียก CLI หรือแอปเรียก CLI ก็ได้ ไม่ต่างกัน

📋 ปล่อยงานรันยาว แล้วยังต้องคอยเช็คอยู่ไหม
🔹 คำวิจารณ์ AI ยุคแรกคือมันทำให้คนหลุดจากภาวะ flow แต่ Peter บอกว่าเขา flow สุดๆ เพราะในหัวมีแผนที่ชัดว่า session ไหนแตะงานส่วนไหน แล้วจัดขอบเขตไม่ให้แต่ละงานเหยียบกันเอง
🔹 สมัยก่อนถ้าพิมพ์ prompt แทรกระหว่างที่ agent ทำงาน มันอาจสับสนหรือหลุดเส้นทาง แต่โมเดลรุ่นปัจจุบันเดินหน้าต่อได้เอง
🔹 กับงานที่รันยาว เขาใช้คำสั่งเรียกดูสถานะโดยไม่ interrupt ตัว agent แล้วนั่งอ่านว่ามันไปถึงไหนแล้ว
🔹 เทคนิคเด็ด: สั่งให้ agent จดบันทึกความคืบหน้าลงไฟล์ เหมือน changelog ประจำโปรเจกต์ แล้วเราแค่เปิดไฟล์นั้นอ่านแทน
🔹 ถ้ามี spec ใหญ่ ให้สั่งเพิ่มว่าต้องบันทึกการตัดสินใจที่เกิดขึ้นระหว่างลงมือด้วย เพราะ spec ไม่มีวันครอบคลุมทุกอย่าง ระหว่างเขียนโค้ด agent จะเจอ edge case หรือเรื่องนอก spec เสมอ
🔹 มันจะไม่หยุดกลางทางเพื่อถามว่า ผมทำไป 20% แล้ว รู้ว่าคุณหลับอยู่ แต่ขอหยุดตรงนี้นะ มันจะตัดสินใจไปเลย ซึ่งบ่อยครั้งคือคำตอบที่เราต้องการอยู่แล้ว ถ้าไม่ใช่ ก็แค่มา review ทีหลังแล้วบอกว่าข้อแลกเปลี่ยนนี้เลือกผิด ทำใหม่อีกรอบ
